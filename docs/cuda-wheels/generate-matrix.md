# generate_matrix.py

The planner: it turns the repo's declarative state into the concrete list of
CI jobs that `build.yml` fans out. Where the files it reads live is mapped in
[the repo breakdown](build-process.md#where-do-the-files-live) — this page
explains what happens between "configs on disk" and "job matrix in CI".

## Inputs

| Input | Role |
|---|---|
| `packages/<name>/` via `package_loader.py` | one flat config dict per package (package.yml + overrides merged; loader hard-errors on undeclared `links_torch` or an undocumented override) |
| `defaults/python_cuda_torch_os_policy.yml` | the shared grid: generated `combinations` rows + `platforms` |
| `defaults/arch_policy.yml` | per-CUDA arch lists, aarch64 table, per-(cuda, torch) exceptions — read at **build** time (CW-ADR-0012) |
| `defaults/phantom_combos.json` | cells the grid implies but upstream never shipped (generated by `derive_defaults.py`) |
| the package's rolling GitHub release | existing wheels, for the skip check |

## The pipeline, per package

1. **Resolve combos.** Priority: the package's own `build_matrix.combinations`
   → legacy cartesian form → the `links_torch: false` collapse (torch is not
   an axis: one build per (cuda, python, platform), newest torch per CUDA line
   as build env, CW-ADR-0011) → inherit the shared grid.
2. **Filter cells.** Drop phantom combos; drop aarch64 cells whose CUDA line
   is absent from `arch_policy_aarch64` (no SBSA toolkit); drop cells whose
   wheel already exists in the release — for torch-free packages the check is
   a wildcard: any torch tag satisfies the (cuda, python, platform) cell.
3. **Resolve the arch list** (`resolve_arch_list`), highest priority first:
   per-combo `arch_list` in the package's own build_matrix →
   `arch_list_by_cuda[cuda]` → static package `arch_list` → the policy row
   (with `arch_exceptions` applied). Every result is normalized so the highest
   non-`a` arch carries `+PTX` (forward compat for future GPUs).
4. **Split into matrices.** `linux` / `windows` / `linux_aarch64` for normal
   jobs; packages with `sharding` also emit `*_link` matrices (the assemble
   step); packages with `sequential_checkpoint > 0` are routed to the
   `linux_chain` / `windows_chain` matrices instead of the plain ones.

## Output

A JSON document of GitHub Actions matrices (`--output`, default
`matrix.json` — not committed). `build.yml` consumes it via
`fromJson(...)`.

```bash
python scripts/generate_matrix.py                     # everything
python scripts/generate_matrix.py --package natten    # one package
python scripts/generate_matrix.py --platform linux    # one platform
```

## Invariants worth knowing

- **Build output is a function of the git SHA.** Nothing here scrapes the
  network for policy; upstream reality enters only through the committed
  snapshot and the generated rows (CW-ADR-0012).
- **The auditor uses the same resolver.** `scripts/audit.py --archs` imports
  `resolve_arch_list` rather than keeping its own arch table, so the planner
  and the verifier cannot disagree.
- **The `+PTX` suffix is part of the contract.** Because the normalizer
  always suffixes the highest arch, any *patch* that parses
  `TORCH_CUDA_ARCH_LIST` into tokens must strip `+` suffixes before
  comparing (`a.split("+")[0]`). Two shipped incidents prove the stakes:
  flash_attn's and sageattn3's bridges matched tokens exactly, so
  `"9.0+PTX"`/`"12.0+PTX"` silently dropped the top arch from every
  wheel (no H100 SASS on cu124/126, no RTX 5090 SASS at all).
- **Skip logic is name-based.** A published wheel satisfies its cell by
  filename; changing arch policy does not re-open cells (rebuilds are a
  deliberate act, see CW-ADR-0013).
